## **新增的需求**

### **需求：图像验证码挑战生命周期**

系统应将图像验证码挑战作为短期存在的验证对象进行颁发，该对象可以被验证一次，然后被消耗或失效。

#### **场景：创建验证码挑战**

- **当** 客户端为一个支持的认证场景请求验证码挑战时
- **那么** 系统将返回一个挑战令牌和图像内容，并存储预期答案及一个短暂的过期时间

#### **场景：成功验证后消耗验证码挑战**

- **当** 客户端成功验证一个验证码挑战时
- **那么** 系统将该挑战标记为不可再用于后续受保护的操作

### **需求：邮箱验证码具有目的范围**

系统应颁发与目标邮箱和特定目的（如 `REGISTER`）绑定的邮箱验证码。

#### **场景：验证码验证检查目标和目的**

- **当** 客户端为注册提交一个邮箱验证码时
- **那么** 系统将根据目标邮箱、`REGISTER` 目的、验证码状态和过期时间来验证该验证码

### **需求：每个目标和目的只允许一个活跃验证码**

系统应确保在给定的目标和目的下，同一时间只有一个验证码处于活跃状态。

#### **场景：新验证码替换之前的验证码**

- **当** 客户端为同一个邮箱和目的请求新的邮箱验证码，而之前的验证码仍然活跃时
- **那么** 系统将之前的验证码标记为已替换，并仅保持最新的验证码为活跃状态

### **需求：验证码为一次性使用并设置尝试次数限制**

系统应强制执行验证码过期、尝试次数限制和一次性消耗语义。

#### **场景：成功验证后消耗验证码**

- **当** 客户端提交一个正确且活跃的验证码时
- **那么** 系统将该验证码标记为已消耗，并拒绝未来任何重复使用它的尝试

#### **场景：尝试次数过多后验证码被冻结**

- **当** 客户端对一个活跃验证码的验证尝试超过了允许的次数时
- **那么** 系统将该验证码标记为已冻结或无效，并要求一个新验证码才能继续

### **需求：验证码发送尝试作为安全事实被保留**

系统应保留验证码的发送尝试结果，以便系统能够区分待发送、已发送和发送失败的状态。

#### **场景：发送提供商失败被记录**

- **当** 系统创建了一个验证码，但下游的邮箱提供商未能成功投递时
- **那么** 系统将带有发送失败结果的验证码对象进行记录，而不是将此次尝试视为从未发生过
