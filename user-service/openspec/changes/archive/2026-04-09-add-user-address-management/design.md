## Context

当前仓库已经具备基于 JWT 的认证能力、当前用户解析能力、统一错误包装以及受保护写操作的风险控制能力，但地址能力仍停留在占位状态：`user_address` 只有 `address_id` 和 `owner_user_id`，`ProtectedWriteController` 也只做地址写前的所有权探测。要支持真实的收货地址管理，需要同时扩展 HTTP API、数据模型、MyBatis 映射、地址领域服务和地址相关测试。

这个变更的复杂点不在 CRUD 本身，而在几个需要持续成立的不变量：同一用户最多 10 条有效地址、同一用户最多一个默认地址、只要仍有有效地址就必须存在默认地址、删除默认地址后自动补位、对不存在地址和越权地址保持相同的外部语义。这些规则跨越 controller、service、mapper 和 schema，适合在编码前先固化为设计约束。

## Goals / Non-Goals

**Goals:**
- 为当前登录用户提供完整的收货地址新增、修改、删除和列表查询能力。
- 以最小 API 集合落地地址能力，保持与现有认证和错误处理风格一致。
- 将默认地址唯一性、地址数量上限、软删除和所有权校验集中在地址服务层统一实现。
- 让现有受保护写入地址校验逻辑复用真实地址查询结果，而不是继续依赖占位式 mapper 查询。

**Non-Goals:**
- 不引入地址详情接口、分页、搜索、标签、经纬度或行政区编码。
- 不引入新的认证模型、Principal 注入方式或新的异常协议。
- 不通过数据库特定特性实现“唯一默认地址”约束，也不引入乐观锁或版本号。
- 不把地址去重、地址标准化或省市区字典管理纳入本次变更。

## Decisions

### 1. 地址 API 使用资源式 CRUD，并仅面向当前登录用户

选择 `GET/POST/PUT/DELETE /api/v1/addresses` 这一组资源式接口，而不是新增动作式 `/create`、`/update`、`/delete` 接口。原因是地址是典型资源对象，资源式路由更适合表达列表、创建、覆盖更新和删除语义，同时也避免把“设默认地址”拆成额外动作接口。

候选方案对比：
- 资源式 CRUD：语义清晰，接口面小，适合地址簿。
- 动作式接口：与现有认证接口风格更接近，但会放大地址模块的动作数量。
- 混合模式：会引入重复语义，增加维护成本。

### 2. 地址领域服务负责维护不变量，数据库仅提供基础持久化

选择在 `DefaultAddressService` 中统一处理地址数量上限、默认地址唯一性、默认地址补位和所有权校验，而不是依赖数据库部分唯一索引或在 controller 层分散处理。原因是当前测试依赖 H2 的 MySQL 兼容模式，不适合引入依赖数据库方言的复杂约束；同时默认地址补位和“有地址必有默认”的规则天然需要服务层事务编排。

候选方案对比：
- 服务层事务维护：与当前仓库一致，跨数据库更稳定。
- 数据库约束维护：在生产数据库可能更强，但会增加 H2 兼容与测试复杂度。
- controller 内散落判断：实现快，但规则容易重复和漂移。

### 3. 地址删除采用软删除，并以 `deleted_at` 表达有效性

选择软删除而不是硬删除，因为地址是高概率会被订单、结算或审计功能复用的资源。软删除允许当前查询层只返回有效地址，同时为未来扩展保留历史数据；地址上限统计也只计算 `deleted_at is null` 的有效地址。

候选方案对比：
- 软删除：兼顾未来扩展和当前可用性。
- 硬删除：实现更简单，但会提前消耗未来演进空间。

### 4. 默认地址规则固定为“唯一默认 + 自动补位”

选择让首条地址自动默认，新增/更新 `defaultAddress=true` 时切换默认，删除默认地址后按最近更新时间补位。这样用户在任意时刻都能获得稳定的默认地址语义，也避免前端在列表页额外处理“当前没有默认地址”的分支。

候选方案对比：
- 唯一默认 + 自动补位：最稳定，也最贴合地址簿场景。
- 唯一默认但可为空：状态更多，前端和实现都更复杂。
- 单独“设默认”接口：不必要地扩大 API 面。

### 5. 并发更新采用最后写入生效

地址模块不引入版本号或乐观锁，两个客户端并发修改同一地址时以后一次写入结果为准。原因是地址簿场景冲突成本低，而引入版本号会增加请求模型、错误语义和测试复杂度，不符合本次变更目标。

候选方案对比：
- 最后写入生效：实现简单，满足 v1。
- 乐观锁：更严格，但当前收益不足以覆盖复杂度。

## Risks / Trade-offs

- [默认地址唯一性完全依赖服务层事务] → 通过将“清空其他默认地址”和“设置当前默认地址”放入同一事务，并在测试中覆盖新增、修改、删除补位路径降低风险。
- [软删除会让 mapper 查询分支变多] → 所有列表、计数、按 ID 查询都明确区分“有效地址”和“原始地址”，避免遗漏 `deleted_at is null` 条件。
- [不存在地址与越权地址统一返回 `OWNERSHIP_VIOLATION` 会隐藏调试信息] → 继续保留内部安全事件和日志，使服务端仍可定位具体原因。
- [最后写入生效可能覆盖并发编辑结果] → 这是有意接受的 v1 取舍，避免为低频冲突场景引入版本控制。
